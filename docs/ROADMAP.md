## 1. 工作流总览

五个阶段，每个阶段有明确的「入口条件」和「出口条件」。**没有出口条件就不进入下一阶段**——这是流程唯一的意义。

| 阶段 | 做什么 | 产出物 | 出口条件 |
|---|---|---|---|
| **0 立项** | 定义问题、范围、非目标 | PRD | 作者确认范围与优先级 |
| **1 设计** | 技术选型、数据结构、界面原型 | 技术方案 + 线框 | 关键决策无未决项（或已记录为风险） |
| **2 实现** | 按里程碑迭代，每个 PR 一个可验证的增量 | 代码 + 测试 + 文档更新 | 里程碑验收标准全部满足 |
| **3 审查** | 自审 + 自动化检查 + 真机走查 | 测试报告 + 问题清单 | 发布标准全部满足（见 PRD §7） |
| **4 发布** | 打 tag、写 CHANGELOG、部署、复盘 | 线上版本 + 复盘记录 | 线上可用 + 回滚方案确认 |

### 阶段 0 与「多次讨论」

讨论是必要的，但**必须有时间盒**：每个议题最多两轮，第二轮结束必须给出结论或记为「未决风险」，不能无限循环。讨论结论写进 PRD 或 ADR，而不是留在聊天记录里——三个月后没人记得当时为什么这么定。

### 为什么不照搬大厂流程

大厂的流程（需求评审、排期、灰度、值班）是为**多人协作与线上事故成本**设计的。一个人做的小项目照搬，只会产生大量没人看的文档。

保留其中真正有用的部分：

- ✅ 需求边界（防止范围膨胀）
- ✅ 变更留痕（PR + CHANGELOG + tag）
- ✅ 自动化门禁（CI 不过就不发布）
- ✅ 可回滚（每次发布可退回上一个 tag）
- ❌ 不做：排期表、周报、形式化评审会、多人 code review 仪式

| 项 | 内容 |
|---|---|

| 项 | 内容 |

| 交付 | 掷币动画、手动录入、本卦/互卦/变卦推演、结果页、分享链接 |

| 项 | 内容 |
|---|---|
| 交付 | 深色模式、卦库检索、历史记录、无障碍修复、性能优化 |

### M4 · 测试与发布（第 5 周）

| 项 | 内容 |
|---|---|
| 交付 | E2E 用例、发布检查清单、CHANGELOG、`v2.0.0` tag、线上部署 |
| 验收 | PRD §7 发布标准全部满足；回滚演练一次 |

> 时间按「业余时间投入」估算，可顺延；**里程碑内容不可在过程中追加**，新想法一律进 v2.1 待办。

## 3. 日常协作约定

| 项 | 约定 |
|---|---|
| 分支 | `main` 保持可发布；功能在 `feat/*`、修复在 `fix/*`、文档在 `docs/*` |
| 提交 | 遵循 Conventional Commits：`feat:` / `fix:` / `docs:` / `test:` / `chore:` |
| PR | 一个 PR 只做一件事；描述里写「改了什么 / 为什么 / 怎么验证」 |
| 合并 | Squash merge，保持 `main` 线性历史 |
| 版本 | SemVer：功能 → MINOR，修复 → PATCH，破坏性 → MAJOR |
| 记录 | 每个版本更新 `CHANGELOG.md`；重要决策写 `docs/adr/NNNN-*.md` |
| Issue | 一个里程碑一组 issue，用标签区分 `p0` / `p1` / `p2` |

## 4. 发布检查清单

发布前逐条勾选，任何一条不满足就不发布：

- [ ] CI 全绿（lint / typecheck / unit / e2e / build）
- [ ] 64 卦数据校验通过，`reviewed: false` 的条目已标注
- [ ] 移动端真机走查（iOS Safari + Android Chrome）
- [ ] 键盘走查：Tab 能到所有控件，焦点可见
- [ ] Lighthouse 移动端三项 ≥ 90
- [ ] 分享链接在无痕窗口可还原
- [ ] 免责声明与 AI 参与说明在页面上可见
- [ ] CHANGELOG 已更新，版本号与 tag 一致
- [ ] 回滚步骤已确认（退回上一个 tag）

## 5. 复盘（每次发布后 15 分钟）

三个问题，写进 `docs/retro/`：

1. 这次发布**最慢的一步**是什么？下次怎么缩短？
2. 有没有**返工**？返工的原因是什么？
3. 哪个假设**被证明是错的**？
