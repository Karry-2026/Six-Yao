# 托管容量与素材预算

写实路线的真正约束不在显卡，而在**首屏要下载多少字节**——以及你的托管配额。

## 1. GitHub Pages 的硬指标

| 项 | 限制 |
|---|---|
| 仓库大小 | 建议 ≤ 1 GB |
| 发布站点大小 | ≤ 1 GB |
| 月流量 | **100 GB（软限制）** |
| 单次部署 | ≤ 10 分钟 |
| 构建频率 | 10 次/小时（用 Actions 不受限） |

## 2. 一次访问要花多少流量

| 单次访问体积 | 100 GB 可支撑的月访问量 |
|---|---|
| 5 MB | ≈ 20,000 次 |
| 8 MB | ≈ 12,800 次 |
| 15 MB | ≈ 6,800 次 |
| 30 MB | ≈ 3,400 次 |

个人项目月访问量通常在几百到几千，**8–15 MB 完全安全**。真正会让站点变慢的是单次体积，不是总量。

## 3. 素材预算（写实路线）

单次访问的目标：**首访 8–12 MB，二次访问（有缓存）< 2 MB**。

| 类别 | 预算 | 说明 |
|---|---|---|
| 环境贴图 HDRI | 1.7 MB（1K HDR） | 只加载一次，用于 IBL 与反射 |
| PBR 材质 | 4 套 × 1.2 MB = 4.8 MB | 每套：albedo + normal + roughness，1K |
| 几何体 | < 1 MB | 程序化为主，必要时加 Draco 压缩的 glTF |
| 字体 | < 300 KB | 思源宋体子集，自托管 |
| 代码 | < 400 KB | three.js + 场景 |

## 4. 关键手段：KTX2 / Basis 压缩

这是写实路线能不能在 10 MB 内做完的关键。

| 格式 | 1K 贴图单张 | 显存占用 | 说明 |
|---|---|---|---|
| PNG | 1.5–3 MB | 解码后 4 MB | 太大 |
| JPG | 200–400 KB | 解码后 4 MB | 可用，但有压缩痕 |
| **KTX2（Basis）** | **60–120 KB** | **压缩态直接上传 GPU（约 0.5 MB）** | ✅ 推荐 |

做法：构建期用 `gltf-transform` 或 `toktx` 把 PNG 转成 KTX2，运行时用 `KTX2Loader` + `KTX2Loader.detectSupport(renderer)` 加载。体积降到 1/4，显存降到 1/8，且没有 JPG 的块状伪影。

## 5. 结论

- 写实路线**可以**做，前提是贴图走 KTX2，单次访问控制在 10 MB 上下；
- 以 10 MB/次计算，100 GB 配额够 **约 10,000 次/月**，个人项目绰绰有余；
- 不做移动端降级是你的决定，技术上没问题；代价只是低端设备帧率与发热，与托管无关。
