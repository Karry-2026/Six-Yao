# ADR-0001 · 放弃 3D 场景，改为 2D 水墨风

- 状态：已接受（2026-11-09）
- 影响：ROADMAP M2；`package.json`、`src/scripts/scene.ts`、全部 3D 资产

## 背景

v2 以 three.js 搭建了程序化 3D 庭院：几何全部代码生成，贴图来自 Canvas 程序化绘制与 Poly Haven CC0 PBR 贴图，另有 HDR 环境光、后处理 Bloom、四时氛围系统。核心渲染逻辑集中在单文件 `scene.ts`（约 1500 行）。

上线后复盘暴露的问题：

1. **视觉不达标**：程序化几何的「廉价感」无法回避——日景呈灰盒质感，夜景靠灯光与粒子勉强成立。美术要达到可发布水准，需要建模、贴图、灯光的持续投入，超出一人项目的承受范围。
2. **维护成本高**：单文件巨型函数、着色器字符串、性能分档与降级链路，任何视觉改动都要穿过大量胶水代码。
3. **体积负担**：HDRI 1.7MB + PBR 贴图约 5MB，挤压首屏预算。

## 决策

v3 **放弃 WebGL 实时 3D，改用 Canvas2D / SVG 手绘水墨风**呈现场景与起卦仪式。

保留：四时氛围（晴昼/烟雨/暮夜/雪夜）概念、起卦的仪式感叙事、无渲染能力时的降级思路。
移除：`three` 依赖、RGBELoader/Bloom 后处理、全部 HDR 与 PBR 资产（预计仓库瘦身约 12MB）。

## 后果

- 正面：美术可控性大增（笔触/留白/构图可逐步打磨）；首屏与运行性能预算宽裕；代码量与依赖大幅缩减；风格统一更容易。
- 负面：失去「可游走的 3D 庭院」这一记忆点；v2 的 3D 投入成为沉没成本。
- 缓解：v2 的 3D 完整保留在 `v2.5.0` tag 与 git 历史中，随时可回溯；若未来需要，2D 层可与 3D 层并存做「双模式」（见 ROADMAP 待办）。
